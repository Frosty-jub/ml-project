# สคริปต์สาธิตงานคนที่ 4

1. แสดง `docker compose ps` เพื่อยืนยันบริการรันในคอนเทนเนอร์และ health check ผ่าน
2. เปิด `/docs` แสดง `POST /predict` กับ `GET /health` และเรียก `/health` ให้เห็นเวอร์ชันโมเดล
3. ส่ง `examples/valid_request.json` ให้เห็นผลทำนาย และอธิบายว่าแต่ละแถวได้ผลหนึ่งค่า
4. ส่ง `examples/missing_value_request.json` อธิบายว่า null ที่ schema อนุญาตจัดการโดย imputer ตัวเดียวกับตอนเทรน
5. ส่ง `examples/invalid_request.json` ให้เห็น HTTP 422 พร้อมชื่อฟีเจอร์ที่ผิด ตรวจ logs ให้เห็นคำขอผิดถูกปฏิเสธ จากนั้นส่งข้อมูลปกติอีกครั้งยืนยันระบบยังพร้อมทำงาน
6. เปิด `/metrics` และ `docker compose logs --tail 20 serving` แสดงจำนวนคำขอ, latency, readiness, request ID
7. รัน load test หรือเปิดรายงานผล JSON แสดง p50/p95, requests/s, จำนวน errors และ `slo_passed` เทียบ `slo.json`
8. ชี้ Pipeline ที่โหลดจากไฟล์เดียวกับที่เทรน และอธิบายการเปลี่ยน `MODEL_DIR` เป็นโมเดลที่ทีมอนุมัติ

**ก่อนนำเสนองานจริง:** ต้องใช้โมเดล/ฟีเจอร์ของกลุ่มและรันทดสอบใหม่ ผลสาธิตข้อมูลสังเคราะห์เป็นหลักฐานว่าส่วน serving ทำงาน ไม่ใช่ผลความแม่นยำของโครงงานกลุ่ม

คำถามที่ควรตอบได้:

- ทำไมต้องใช้ Pipeline? เพื่อใช้ preprocessing ที่ fit จากชุดฝึกแล้วเหมือนเดิมขณะให้บริการ ไม่ fit ซ้ำบนคำขอ
- ข้อมูลเสียทำอย่างไร? ปฏิเสธก่อน inference ด้วย 422; log/metrics บันทึกไว้ บริการไม่ล่ม
- โมเดลหายทำอย่างไร? `/health` และ `/predict` ตอบ 503; `serving_model_ready=0`
- p50/p95 ต่างกันอย่างไร? p50 คือเวลาที่ครึ่งหนึ่งของคำขอเร็วกว่า; p95 คือเวลาที่ 95% ของคำขอเร็วกว่า
- Throughput วัดอย่างไร? จำนวน HTTP requests ที่ทำนายสำเร็จหารด้วยระยะเวลารวมของช่วงทดสอบ
- โมเดลใหม่มาแล้วทำอย่างไร? export เวอร์ชันที่อนุมัติไป directory ใหม่ เปลี่ยน `MODEL_DIR`, restart และตรวจ `/health`; นโยบายอนุมัติ/rollback อยู่ที่สมาชิก Registry
- ระบบนี้ตรวจ drift หรือไม่? ยังไม่ตรวจเอง แต่ส่ง metrics/logs ให้คนที่ 5 และต้องตกลงข้อมูลเพิ่มเติมสำหรับตรวจ drift
