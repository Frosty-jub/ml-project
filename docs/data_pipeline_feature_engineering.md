# Data Pipeline + Feature Engineering (งานคนที่ 1)

เอกสารนี้อธิบายขั้นตอนจาก Online Retail II ถึงข้อมูลที่เพื่อนในทีมใช้ฝึกโมเดลได้ โดยอ้างอิงกฎที่รันจริงใน [`config/pipeline.json`](../config/pipeline.json) และผลการประมวลผลข้อมูลจริง ณ วันที่ 26 กันยายน 2026

## วิธีสร้างข้อมูลซ้ำ

ติดตั้ง Python และ dependencies ตาม [`README.md`](../README.md) แล้วรันจากโฟลเดอร์หลัก:

```bash
python scripts/run_data_pipeline.py
```

คำสั่งนี้ทำตามลำดับ: ดาวน์โหลด/แตก ZIP (ข้ามเมื่อมีไฟล์แล้ว) → ตรวจ schema และเตรียมข้อมูล → Data Validation → สร้าง features และแบ่ง train/validation/test หากขั้นใดล้มเหลว คำสั่งหยุดทันที ไฟล์ข้อมูลที่สร้างอยู่ใน `data/` และไม่ขึ้น GitHub

หากต้องการทำทีละขั้น ให้รัน `scripts/download_data.py`, `scripts/prepare_data.py`, `scripts/validate_data.py`, `scripts/build_features.py` ตามลำดับ ส่วน `python scripts/run_eda.py` สร้าง [รายงาน EDA](../reports/eda_summary.md) และกราฟเพื่อสำรวจข้อมูล

## 1. Load และ clean ข้อมูลดิบ

สคริปต์อ่านทั้งสอง sheet ของ workbook, แปลง `StockCode` เป็นข้อความ, ตรวจคอลัมน์หลัก (`Invoice`, `StockCode`, `Quantity`, `InvoiceDate`) ว่าอ่านได้และไม่ว่าง จากนั้นใช้กฎดังนี้:

| กฎ | เหตุผล |
|---|---|
| ตัด invoice ที่ขึ้นต้น `C` | เป็นรายการยกเลิก ไม่ใช่ยอดขายใหม่ |
| ตัด `Quantity <= 0` | ไม่รวมรายการคืนหรือปรับลดใน target ยอดขายบวก |
| ตัด `POST`, `DOT`, `BANK CHARGES`, `AMAZONFEE`, `ADJUST`, `D`, `B`, `S` | คำอธิบายที่พบใน EDA ระบุค่าขนส่ง ค่าธรรมเนียม การปรับบัญชี ส่วนลด หรือ sample ไม่ใช่สินค้าคงคลังที่จะพยากรณ์ |
| คงแถวที่เหมือนกันทุกคอลัมน์ | ไฟล์ไม่มีรหัสบรรทัดธุรกรรม จึงแยกไม่ได้ว่าซ้ำผิดพลาดหรือซื้อสินค้าเดียวกันหลายบรรทัด การลบอาจทำให้ยอดขายต่ำเกินจริง |
| ไม่ตัด `Price <= 0` อัตโนมัติ | `Price` ไม่ใช่ข้อมูลที่ใช้คำนวณ target; กรณีราคาศูนย์ควรตรวจแยกก่อนตั้งกฎใหม่ |

EDA พบแถวที่เหมือนกันทุกคอลัมน์ 34,335 แถว และแถว `Price <= 0` 6,207 แถว จึงบันทึกเป็นข้อสังเกต ไม่ตีความว่าเป็นข้อมูลผิดทั้งหมด รหัส `M` และ `m` มีคำอธิบาย Manual ซึ่งยังกำกวม จึงยังไม่ตัดออก กฎรหัสที่ตัดนี้เป็นชุดเริ่มต้นแบบระมัดระวัง ให้ทีมทบทวนก่อนล็อกการทดลองโมเดล

| จำนวนแถว | ผล |
|---|---:|
| ข้อมูลดิบทั้งสอง sheet | 1,067,371 |
| invoice ยกเลิก | 19,494 |
| `Quantity <= 0` หลังตัด invoice ยกเลิก | 3,457 |
| รหัสที่ไม่ใช่สินค้าในแถวขายบวก | 3,425 |
| แถวขายบวกที่ใช้รวมรายวัน | 1,040,995 |

## 2. Aggregate รายวันและสร้าง target

รวม `Quantity` ตาม `(sku_id, date)` แล้วเติมวันที่ไม่มีธุรกรรมเป็น `0` ตั้งแต่วันขายครั้งแรกที่พบของ SKU นั้นถึงวันสุดท้ายของข้อมูล ข้อมูลไม่มีสถานะสินค้าคงคลัง จึงแยกไม่ได้ว่าวันศูนย์เกิดจากไม่มีคนซื้อหรือสินค้าหมด

ณ วัน origin `t` หลังปิดยอดวันนั้น:

```text
demand_next_7d_units(sku, t) = ผลรวม daily_sold_units ของวันที่ t+1 ถึง t+7
```

วันสุดท้ายที่พบยอดขายคือ 2011-12-09 จึงสร้าง label ได้ถึง origin 2011-12-02 เท่านั้น ผลลัพธ์:

| ไฟล์ในเครื่อง | แถว | ความหมาย |
|---|---:|---|
| `data/interim/sku_daily_sales.csv.gz` | 3,078,994 | ยอดขาย SKU รายวันเต็มช่วง ใช้ตรวจ target |
| `data/processed/sku_daily_demand_7d.csv.gz` | 3,044,168 | รายวันพร้อม target ที่มีอนาคตครบ 7 วัน |

ไฟล์เต็มมี 4,976 SKU ส่วนไฟล์ label มี 4,975 SKU เพราะหนึ่ง SKU เริ่มขายใน 7 วันท้ายและยังสร้าง label ไม่ได้

## 3. Data Validation

[`scripts/validate_data.py`](../scripts/validate_data.py) ตรวจทั้งตารางรายวันและตาราง label:

- มีคอลัมน์หลักครบ ไม่มีค่าว่าง และวันที่อ่านได้
- คีย์ `(sku_id, date)` ไม่ซ้ำ; ยอดขายและ target เป็นจำนวนเต็มไม่ติดลบ
- วันของแต่ละ SKU ต่อเนื่องและไปถึงวันสุดท้ายของชุดข้อมูล
- แต่ละ label ตรงกับ SKU และวันในตารางเต็ม และเท่ากับผลรวมยอดขายของ 7 วันถัดไป **ทุกแถว**

การรันจริงผ่านทั้งหมด: 3,044,168 label ตรวจครบ, target ที่ผิด 0 แถว รายงานเครื่องอ่านได้อยู่ที่ `reports/generated/validation_summary.json` ซึ่งถูกกันออกจาก Git เพื่อไม่เก็บผลรันเก่าปะปนกับโค้ด สคริปต์สร้าง features ตรวจ checksum ของข้อมูลและ config กับรายงาน validation เพื่อกันการใช้ผลตรวจที่หมดอายุ

## 4. Feature Engineering

หนึ่งแถวของโมเดลคือ `(sku_id, forecast_origin_date)` feature ใช้ข้อมูลถึงวัน origin `t` เท่านั้น:

| คอลัมน์ | นิยาม |
|---|---|
| `daily_sold_units` | ยอดขายของวัน `t` หลังปิดยอด |
| `sales_lag_1`, `sales_lag_7`, `sales_lag_14`, `sales_lag_28` | ยอดขายของ `t−1`, `t−7`, `t−14`, `t−28` |
| `sales_rolling_sum_7`, `_14`, `_28` | ผลรวมยอดขายย้อนหลังตามจำนวนวัน โดย **รวมวัน `t`** |
| `day_of_week` | วันในสัปดาห์ของ `t` (จันทร์=0 ถึงอาทิตย์=6) |
| `month` | เดือนของ `t` (1–12) |
| `is_weekend` | `1` เมื่อ `t` เป็นเสาร์หรืออาทิตย์ |
| `days_since_first_sale` | จำนวนวันนับจากวันขายครั้งแรกที่พบของ SKU |
| `demand_next_7d_units` | target สำหรับฝึก/ประเมิน **ห้ามใช้เป็น feature** |

ตัด 28 วันแรกของแต่ละ SKU เพื่อให้ `lag_28` และ rolling ทุกช่วงมีประวัติครบ 138,801 แถวถูกตัดด้วยกฎนี้ ไม่มีการเติม feature จากอนาคต การเข้ารหัส SKU, การ scale และการเลือก feature เพิ่มเติมต้อง fit จาก train เท่านั้น แล้วนำตัวแปลงเดิมไปใช้กับ validation/test

## 5. Time Split

แบ่งตามวัน origin โดยไม่สุ่ม และให้วันสิ้นสุดของ target (`t+7`) อยู่ในช่วงที่กำหนด:

| ชุด | วัน origin ที่ได้จริง | จำนวนแถว | จำนวน SKU |
|---|---|---:|---:|
| train | 2009-12-29 ถึง 2011-06-23 | 2,141,532 | 4,522 |
| validation | 2011-07-01 ถึง 2011-09-23 | 394,699 | 4,700 |
| test | 2011-10-01 ถึง 2011-12-02 | 304,547 | 4,939 |

origin วันที่ 24–30 มิ.ย. และ 24–30 ก.ย. ไม่ใช้ เพื่อไม่ให้ช่วง target 7 วันข้ามขอบเขตชุดข้อมูล รวม 64,589 แถวที่ไม่ถูกจัดลง split การใช้ประวัติยอดขายก่อนช่วง validation/test เพื่อสร้าง feature ทำได้ เพราะ ณ วัน origin ข้อมูลดังกล่าวเกิดขึ้นแล้ว

ไฟล์ส่งต่อเพื่อนทำโมเดลอยู่ที่ `data/processed/train_features_7d.csv.gz`, `validation_features_7d.csv.gz`, `test_features_7d.csv.gz` และมีจำนวนแถว/ช่วงวันที่/ชื่อ feature ใน `reports/generated/feature_split_manifest.json` ให้เพื่อนสร้างเองจาก GitHub ด้วยคำสั่งเดียวด้านบน

## ข้อจำกัดและสิ่งที่เพื่อนทำโมเดลต้องรู้

- Target คือ **ยอดขายที่สังเกตได้** ไม่ใช่ความต้องการจริงเมื่อสินค้าหมด เพราะไม่มีข้อมูล stock-on-hand
- SKU ที่เริ่มขายหลังช่วง train อาจปรากฏใน validation/test: พบ 178 SKU ใน validation และ 417 SKU ใน test ที่ไม่เคยอยู่ใน train โมเดลต้องรับมือรหัสที่ไม่เคยเห็น หรือรายงานผลเฉพาะกลุ่ม SKU ที่มีประวัติ train แยกต่างหาก
- วันยอดขายเป็นศูนย์มีจำนวนมาก และ SKU หลายตัวมีประวัติสั้น ควรเปรียบเทียบ baseline ที่เหมาะกับข้อมูลขายไม่สม่ำเสมอ
- กฎรหัสที่ไม่ใช่สินค้าและการคงแถวซ้ำเป็นสมมติฐานที่บันทึกไว้ หากทีมเปลี่ยนกฎ ให้แก้ `config/pipeline.json` แล้วรัน pipeline ใหม่ทั้งชุด ไม่แก้ CSV ด้วยมือ
