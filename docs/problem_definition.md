# นิยามปัญหาและ target

## ปัญหาที่ต้องการแก้

ผู้ดูแลสินค้าต้องประเมินยอดขายของสินค้าแต่ละ SKU ล่วงหน้าเพื่อประกอบการวางแผนคงคลัง โครงงานเริ่มจากพยากรณ์จำนวนหน่วยขายในช่วงสั้นที่นิยามได้ชัดและวัดผลย้อนหลังได้

## ผู้ใช้และการตัดสินใจ

- ผู้ใช้เป้าหมาย: ผู้ดูแลร้านหรือผู้วางแผนสินค้าคงคลัง
- คำถามของระบบ: “จากข้อมูลที่ทราบถึงวันนี้ SKU นี้จะขายกี่หน่วยในเจ็ดวันปฏิทินถัดไป?”
- ผลลัพธ์ขั้นแรก: ค่าพยากรณ์หน่วยขายสะสมเจ็ดวันต่อ SKU
- การนำไปตัดสินใจ: ใช้เป็นข้อมูลประกอบการเติมสินค้าเมื่อมีข้อมูล stock-on-hand, ระยะเวลาจัดส่ง และนโยบาย safety stock เพิ่มเติม

## หน่วยการพยากรณ์

หนึ่งแถวแทนคู่ `(sku_id, forecast_origin_date)` โดย `forecast_origin_date` คือวันที่ข้อมูลล่าสุดที่มีให้กับโมเดล และถือว่าปิดยอดของวันนั้นแล้ว

`demand_next_7d_units` คือผลรวมจำนวนหน่วยขายของ SKU เดียวกันในวันที่ `forecast_origin_date + 1` ถึง `forecast_origin_date + 7` แบบรวมวันต้นและวันปลาย ตัวอย่างเช่น origin วันที่ 1 มกราคม จะรวมวันที่ 2 ถึง 8 มกราคม ค่า target เป็นจำนวนเต็มไม่ติดลบ

นิยามเชิงคณิตศาสตร์:

```text
target(sku, t) = sum(daily_sold_units(sku, d))
                  for d in [t + 1 day, t + 7 days]
```

วันที่ไม่มีรายการขายในข้อมูลที่เตรียมแล้วนับเป็น 0 หน่วย จุดตัดของ train/validation/test ต้องเป็นวันที่ตามลำดับเวลา ห้ามสุ่มแถวข้ามเวลา และ feature ต้องคำนวณจากข้อมูลไม่เกิน origin date เพื่อป้องกัน target leakage

## ขอบเขตของ label ชุดแรก

label ใช้ยอดขายบวกที่สังเกตได้จาก UCI Online Retail II เท่านั้น:

1. ตัด invoice ที่เลขที่ขึ้นต้นด้วย `C` ซึ่ง UCI อธิบายว่าเป็นรายการยกเลิก
2. ตัด `Quantity <= 0` ซึ่งเป็นรายการคืนหรือปรับลด ไม่ให้นำมาหักออกจากหน่วยขายใน target ชุดแรก
3. รวม `Quantity` ตาม SKU และวันปฏิทิน
4. เติมวันที่ไม่มีธุรกรรมเป็นศูนย์

หลังทำ EDA รอบแรก โค้ดตัดรหัสค่าขนส่ง/ค่าธรรมเนียมที่ระบุชัดใน `config/pipeline.json` และคงแถวที่เหมือนกันทุกคอลัมน์เพราะไม่มีรหัสบรรทัดธุรกรรมสำหรับพิสูจน์ว่าซ้ำผิดพลาด เหตุผลและจำนวนแถวอยู่ใน [`data_pipeline_feature_engineering.md`](data_pipeline_feature_engineering.md) ทีมควรทบทวนกฎก่อนล็อกชุดข้อมูลสำหรับการทดลองโมเดล

## ข้อจำกัดที่ต้องสื่อสาร

UCI Online Retail II เป็นประวัติธุรกรรม ไม่ได้ให้ snapshot ของสินค้าคงเหลือ การเติมสินค้า หรือช่วงที่สินค้าไม่มีของขาย ดังนั้นยอดขายที่สังเกตได้อาจต่ำกว่าความต้องการจริงเมื่อของหมด และระบบรุ่นแรกไม่ควรเรียกผลลัพธ์ว่า “จำนวนที่ต้องสั่ง” หรืออ้างว่าลด stockout ได้โดยไม่มีข้อมูลและการประเมินดังกล่าว

ข้อมูลมีช่วงเวลาประมาณสองปีและเป็นร้านเดียว สัญญาณฤดูกาลระยะยาวและการยืนยันผลกับร้านอื่นจึงมีข้อจำกัด
